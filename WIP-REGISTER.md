### Task 1 — CurrentActiveIdpValuesResponse (priority-1 spine): GENUINE GAP FOUND, NOT ADOPTED

**`gh pr diff 102 --repo jwoglom/pumpx2`** read directly (not WebFetch-summarized, per Pitfall 3). The literal diff for `CurrentActiveIdpValuesResponse.java`:

- **Old (pre-fix, matches the current pinned `main`/submodule) doc'd layout:** byte 4 = padding, bytes 5-6 = `currentTargetBg` (uint16, overlapping byte 6 with `currentInsulinDuration`).
- **PR #102's fixed layout:** bytes 4-5 = `currentTargetBg` (uint16, non-overlapping), bytes 6-7 = `currentInsulinDuration`, bytes 8-9 = `currentIsf`.
- **The fix is backed by a genuine hardware capture already present in upstream's OWN test suite before PR #102** (`testCurrentActiveIdpValuesResponse_parseCargo_CapturedPayload`, cargoHex `7017000073002c012800`) — PR #102 only corrects a previously-WRONG assertion on that pre-existing capture (was asserting `currentTargetBg == 11264`, now asserts `115`) and fixes `parse()`/`buildCargo()` to match. This is not a hypothetical fix; it's a correction against real pump bytes already checked into the test suite.

**Independent re-derivation (hand-decoded the literal hex myself, not trusting the PR's stated values):** `raw = [0x70,0x17,0x00,0x00,0x73,0x00,0x2c,0x01,0x28,0x00]`.
  - `carbRatio` = u32LE@0 = 6000 (6.0 g/U) — same under every layout.
  - **TandemKit's CURRENT implementation** (`Sources/TandemMessages/Responses/Responses.swift:767`, `currentTargetBg = Int(raw[5])`) decodes this capture's `currentTargetBg` = `raw[5]` = **`0x00` = 0**.
  - PR #102's fixed layout (u16LE@4) decodes `raw[4],raw[5]` = `0x73,0x00` = **115** — matches the real captured value the PR cites.
  - The OLD pre-fix upstream layout (u16LE@5, overlapping) decodes `raw[5],raw[6]` = `0x00,0x2c` = **11264** — matches the PR's stated "before" bug value.
  - `currentInsulinDuration` = u16LE@6 = `0x2c,0x01` = 300 ✓ (unaffected by the targetBg question either way). `currentIsf` = u16LE@8 = `0x28,0x00` = 40 ✓.

**Assessment:** `currentTargetBg` currently **always decodes as 0** on real Tandem pump hardware whenever bytes 4-5 encode a nonzero target BG the way the captured payload does (target 115 mg/dL is a completely ordinary IDP target). This is a genuine, real-world decode bug in a dose-path-adjacent status-read message (bolus-calculator target BG), not a hypothetical.

### Task 1 — controlX2 pairing-recovery lesson (dirty-BLE-shutdown) + issue #159 cross-check vs `PumpBLEClient`

**controlX2 commit `9d9510678`** ("fix post-pair \"invalid pairing code\" by avoiding dirty BLE shutdown", `main`, 2026-05-04) read via `gh api repos/jwoglom/controlx2/commits/9d9510678 -H "Accept: application/vnd.github.v3.diff"` (the literal diff, not the title — Assumption A4 resolved). The actual bug: controlX2's `triggerAppReload()` calls Android's `Runtime.exit(0)` to hard-kill and relaunch the process (used for settings changes, device-role swaps, etc.) — **without first cancelling the open BLE GATT connection**. Killing the process out from under an open link leaves the pump peer in a "peer vanished" state; the NEXT reconnect renegotiates to a high-latency link and silently drops the JPAKE3 message, surfacing to the user as a spurious "pairing code was invalid" on their very next pair attempt (nothing to do with the code actually being wrong). The fix: a `registerAppReloadShutdownHook`/`shutdownAndAwaitDisconnect(timeoutMs)` pair that synchronously cancels the peripheral connection and BLOCKS (via a `CountDownLatch`) for the GATT-level disconnect callback (up to 600ms) before `Runtime.exit(0)` actually runs.

**Cross-check against `PumpBLEClient` (`Sources/TandemBLE/PumpBLEClient.swift`):** **NO ANALOGOUS GAP** —
- The bug's root cause (an OS-process kill/relaunch that bypasses the BLE teardown path entirely) has no TandemKit-Sources equivalent: TandemKit is a Swift package with no `Runtime.exit(0)`-style app-reload primitive of its own; it never restarts the host process. The closest TandemKit concept — an app being backgrounded/terminated by iOS — is handled via CoreBluetooth's own state-restoration mechanism (`willRestoreState`, `PumpBLEClient.swift:660-671`, invoked with `failClosed(resumePending: false)` first), which is architecturally the OPPOSITE of controlX2's problem: iOS's CoreBluetooth central can itself survive app termination (when configured with a `restoreIdentifier`, `init(restoreIdentifier:)` line 226-233) and hand the live peripheral back on relaunch, rather than requiring the app to race a process-kill against a graceful disconnect.
- TandemKit's own explicit, single-caller-initiated `disconnect()` (line 426-431) already does the sanctioned pattern the controlX2 fix retrofits: it synchronously calls `central.cancelPeripheralConnection(p)` and the resulting `didDisconnectPeripheral` callback (line 697-741) unconditionally runs `failClosed(resumePending: true)` — reset write policy to `.readOnly`, resume every pending transaction with `.connectionLost` — before deciding whether to auto-reconnect. There is no window where TandemKit tears down a link without going through this fail-closed path.
- **Conclusion: no port needed.** The controlX2 LESSON ("never leave a GATT link torn down non-gracefully right before the next pairing attempt") is already satisfied by TandemKit's architecture (CB state restoration in lieu of process-kill-reload; single fail-closed teardown path for every disconnect). Not surfaced as an adoption candidate — there is no gap to adopt against.

### Task 2 — PR #102 JPAKE-adjacent cross-check + priority-4 controlX2 PRs + `TandemAuth` log-hygiene + txId→09.11 pointer

(b) the one-of-two-present transient window falls back to the pairing code in BOTH versions; NEW adds an explicit debug log distinguishing it from case (a), plus a 6-test regression suite (`PumpStateSupplierTest.java`) pinning all five branches.
